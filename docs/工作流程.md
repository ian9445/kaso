# 分支與版本規範

## 一條鐵律

**`main` 不動。** 所有人的所有修改都在分支上進行。

---

## 分支結構

```
main                    ← 原始版本，任何人都不直接推
 └── dev                ← 我們的工作主幹，所有分支從這裡開
      ├── feat/xxx      ← 要改東西就從 dev 再開一個
      ├── feat/yyy
      └── fix/zzz
```

**兩層規則：**

1. 從 `main` 開出 `dev` — 這是我們的主幹
2. 要在 `dev` 上改東西 → **再從 `dev` 開一個子分支**，改完合回 `dev`
3. `dev` 什麼時候合回 `main` → 由團隊決定，不自動合

## 分支命名

| 前綴 | 用在 | 例子 |
|---|---|---|
| `feat/` | 新功能 | `feat/quiz-onboarding` |
| `fix/` | 修 bug | `fix/budget-calc` |
| `style/` | 只動樣式 | `style/product-card` |
| `docs/` | 只動文件 | `docs/changelog` |

---

## 日常操作

**開一個新的子分支**
```bash
git checkout dev
git pull origin dev
git checkout -b feat/你的功能
```

**做完之後**
```bash
git add -A
git commit -m "feat: 加上二選一問答"
git push -u origin feat/你的功能
```

**合回 dev**
```bash
git checkout dev
git merge feat/你的功能
git push origin dev
```

## Commit 訊息格式

```
<類型>: <一句話說明>
```

| 類型 | 意思 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `style` | 樣式、排版 |
| `docs` | 文件 |
| `refactor` | 重構，行為不變 |
| `chore` | 雜項（設定、相依） |

例：
```
feat: 六類分類預算取代單一總額
fix: 重複點擊「算出我的預算」會出錯
docs: 補上 CHANGELOG v0.2.0
```

---

## 版本記錄

每次要合回 `dev` 之前，**先更新 `CHANGELOG.md`**，寫在「未發布」那一節。

分成三類寫：

- **新增** — 多了什麼
- **變更** — 原本有、但做法改了
- **移除** — 拿掉了什麼、為什麼

真的要出一個版本時，把「未發布」改成版號 `[v0.2.0] — 日期`，然後打 tag：

```bash
git tag -a v0.2.0 -m "架構驗證版"
git push origin v0.2.0
```

---

## 注意

- 一次一件事。一個分支只做一個功能，不要混著改
- push 之前先 `git pull`，避免蓋掉別人的東西
- 有疑問先問，不要直接動 `main`
